# LabKit Apps Script setup

This package prepares the private Google Sheet to act as LabKit Manager's
no-cost database and backend. It uses the spreadsheet owner's Apps Script
permissions, so the service-account JSON key is **not** needed here and should
not be copied into the website or Apps Script.

## What this initializer creates

It adds these tabs without changing the existing default tab:

- `Components`, `Kits`, `KitItems`, `KitItemRequirements`, `KitVersions`,
  `KitLineupVersions`, `SemesterKitVersions`
- `Semesters`, `SalesSummary`, `SemesterKits`, `Inventory`, `PackedKitInventory`,
  `BagInventory`
- `VendorQuotes`, `Orders`, `OrderLines`, `Alternatives`
- `Users`, `AuditLog`, `ChangeHistory`, `AppState`

It also reconciles `Users` to the one dedicated LabKit account,
`HKNLabSuppliesGatech@gmail.com`. Running it again is safe when the header rows
still match. If a populated tab has an unexpected header, the initializer stops
and leaves that tab unchanged.

## Install and initialize the backend

1. In the Apps Script editor, open `Code.gs`.
2. Select everything in that file and replace it with the contents of this
   repository's `apps-script/Code.gs`.
3. Click **Project Settings** (the gear on the left).
4. Turn on **Show "appsscript.json" manifest file in editor**.
5. Return to **Editor**, open `appsscript.json`, and replace it with the
   contents of this repository's `apps-script/appsscript.json`.
6. Confirm the Script Properties in **Project Settings** contain:

   - `LABKIT_SPREADSHEET_ID` = `1GeEXuTzxeWavpbnhNO1jfYhGnHTnoZcIIiQJAb1i4D8`
   - `LABKIT_FIREBASE_API_KEY` = the Firebase web API key already used by the app

   The older `LABKIT_INITIAL_ADMIN_EMAIL` property can be deleted; single-account
   mode no longer reads it.

   Add these optional server-only properties to turn on AI and verified supplier
   pricing. Never put any of them in `Index.html` or `src/firebase-config.js`.

   - `LABKIT_GEMINI_API_KEY` = an API key created in Google AI Studio
   - `LABKIT_GEMINI_MODEL` = `gemini-2.5-flash` (optional override)
   - `LABKIT_MOUSER_API_KEY` = a Mouser Search API key
   - `LABKIT_NEWARK_API_KEY` = a Newark/element14 Product Search API key
   - `LABKIT_DIGIKEY_CLIENT_ID` = DigiKey production application client ID
   - `LABKIT_DIGIKEY_CLIENT_SECRET` = DigiKey production application secret
   - `LABKIT_DIGIKEY_ACCOUNT_ID` = the account ID required by DigiKey's
     two-legged pricing request

   Gemini and the supplier integrations are deliberately optional. Without a
   Gemini key, the app uses a weighted historical forecast and requires manual
   component-requirement review. Without supplier credentials, it shows clearly
   labeled planning estimates and never calls those providers. API or quota
   failures do not create a purchase or overwrite a plan.

   For a strict no-cost setup, leave billing disabled on the Gemini API project.
   Free-tier limits can change and a quota error simply activates LabKit's local
   forecast fallback. Google's Gemini pricing page also states that free-tier
   content may be used to improve its products, so LabKit sends only aggregate
   sales history, component specifications, kit requirements, and the planning
   note entered in the dialog—never the Firebase token, email, or Sheet ID.

7. Click **Save project**.
8. At the top of the editor, choose `initializeLabKit` in the function menu.
9. Click **Run** and approve the Google permissions. Google may show an
   unverified-app warning because this is your own private script; use
   **Advanced**, then continue to the project only if the project name and
   Google account are yours.
10. Return to the spreadsheet. Confirm the new tabs exist and open `Users`.
    Your email should be the only seeded row, with role `admin` and `active`
    set to `TRUE`.

The seeded `Users.uid` cell is intentionally blank at this stage. The backend
fills it after the first successful verified sign-in for the dedicated account.

## Add the web interface

After `initializeLabKit` completes successfully:

1. Replace `Code.gs` one more time with the current repository version of
   `apps-script/Code.gs`. This version serves the completed interface.
2. In the Apps Script editor, click **+** next to **Files**, then choose
   **HTML**.
3. Name the new file `Index`. Apps Script displays it as `Index.html`.
4. Replace everything in `Index.html` with the complete contents of this
   repository's generated `apps-script/Index.html` file.
5. Save the Apps Script project.

`Index.html` is generated by `npm run build`; do not edit the generated copy by
hand. Make frontend changes in the source files and rebuild it instead.

## Deploy the web app

Before deploying, open **Firebase Console → Authentication → Users**. Delete
the earlier test accounts, then add `HKNLabSuppliesGatech@gmail.com` with a
password known to the club officers. If that account already exists, use
LabKit's **Forgot password?** flow instead. LabKit no longer offers public
account creation.

1. Click **Deploy → New deployment**.
2. Next to **Select type**, click the gear and choose **Web app**.
3. Use a description such as `LabKit initial release`.
4. Set **Execute as** to **Me**. This lets the server access the private Sheet
   without sharing that Sheet with every club member.
5. Set **Who has access** to **Anyone**. Firebase still restricts the application
   to the dedicated LabKit account. If the public **Anyone** option is absent, a
   Google Workspace administrator may have disabled external web-app access.
6. Click **Deploy**, approve the requested permissions, and copy the `/exec`
   web-app URL.
7. Open the URL and sign in with `HKNLabSuppliesGatech@gmail.com`. If Firebase
   says the address is unverified, click **Resend email**, open the message in
   Gmail, and return to LabKit.

On the first sign-in, the app will:

- fill the blank Firebase UID in the administrator's `Users` row;
- seed the empty `AppState` tab with the application data;
- populate the readable normalized tabs; and
- add the first versioned save to `AuditLog`.

Keep the `/exec` URL as the club's app link. When code changes later, use
**Deploy → Manage deployments → Edit**, select **New version**, and deploy it.

## Automatic GitHub deployment

The repository includes `.github/workflows/deploy-apps-script.yml`. Once
configured, every push to `main` runs the tests and build, pushes the generated
Apps Script files, and updates the existing web-app deployment. The app does
not pull GitHub at page-load time, and its `/exec` URL does not change.

One-time setup:

1. While signed in as the Google account that owns the Apps Script project,
   enable the Apps Script API at <https://script.google.com/home/usersettings>.
2. On a trusted computer, run:

   ```sh
   npx --yes @google/clasp@3.4.1 login
   ```

3. In Apps Script, open **Project Settings** and copy the **Script ID**. This is
   not the deployment ID and it is not the spreadsheet ID.
4. In GitHub, open **Settings → Secrets and variables → Actions** and create
   these repository secrets:

   - `CLASPRC_JSON`: the complete contents of `~/.clasprc.json` created by the
     clasp login. This contains a sensitive refresh token.
   - `CLASP_JSON`: `{"scriptId":"YOUR_SCRIPT_ID","rootDir":"apps-script"}`
   - `APPS_SCRIPT_DEPLOYMENT_ID`: the ID from the current `/exec` deployment
     (the long value beginning with `AKfy...`).

5. In the same GitHub screen, open **Variables** and create
   `APPS_SCRIPT_DEPLOY_ENABLED` with the value `true`.
6. Run **Actions → Deploy LabKit to Apps Script → Run workflow** once. After it
   succeeds, later pushes to `main` deploy automatically.

Treat `CLASPRC_JSON` like a password. Only trusted repository administrators
should be able to change the deployment workflow or read repository secrets.
Do not edit `Code.gs` or `Index.html` directly in Apps Script after enabling
automation because the next GitHub deployment will replace those files.

Schema initialization remains intentionally manual. When a release adds a new
Sheet tab or header, run `initializeLabKit` once before or immediately after
deploying that release; the GitHub workflow does not mutate the spreadsheet
schema automatically.

### Updating an existing LabKit deployment

For the inventory, versioned-kit, order-history, AI-planning, and verified-pricing update:

1. Replace the Apps Script `Code.gs` with the current repository copy and save.
2. Run `initializeLabKit` once more. This creates `KitVersions`,
   `SemesterKitVersions`, `ChangeHistory`, and `BagInventory`, and safely
   appends the new packed-inventory, kit-version packaging, and order columns.
   Existing matching tabs and data are retained.
3. Replace the Apps Script `Index.html` with the current generated copy in
   `apps-script/Index.html` and save.
4. Open **Deploy → Manage deployments**, edit the active web app, choose
   **New version**, and deploy. The `/exec` URL stays the same.

The next session that receives edit access automatically migrates the previous
generated history to the supplied Spring 2015–Fall 2026 records. User-created
future semesters are retained.

## How planning and pricing work

- **Packed inventory is calculated from real sales.** Enter the number prepared
  or received; LabKit subtracts the selected semester's recorded sales and then
  excludes faulty/reserved kits from the available quantity. Loose components
  remain physical counts.
- **Kit BOMs are versioned.** A Planning-semester edit creates a new version and
  leaves prior semester definitions unchanged. Officers can carry a version
  forward, return to an older version, or delete an unused/redundant version.
- **Orders retain paid prices.** Bulk and one-off orders share one ledger with
  semester links, notes, exact line prices, and a receipt/Drive URL.
- **Only the immediately next academic semester uses today's stock.** On plan
  creation, LabKit captures a reviewable allocation: packed kits first, then
  loose components for the remaining kits. A farther-future plan forecasts
  demand but does not subtract the same physical stock twice.
- **Gemini only suggests.** The backend sends aggregate history, kit IDs, and
  officer planning notes. It asks for schema-constrained JSON, validates every
  returned ID and quantity, and shows a draft that an officer can edit before
  creation.
- **Supplier APIs provide prices.** Mouser, DigiKey, and Newark responses are stored with
  a check time, order quantity, minimums, and price breaks. Gemini may compare
  supplier descriptions with per-kit requirements, but it never invents or
  changes a supplier price. Shipping is not assumed when the supplier API does
  not return it.
- **Adding a component from a vendor uses Gemini, not the supplier APIs.** In the
  component dialog an officer enters a vendor, a part number or SKU, and
  optionally a product link; Gemini searches the web and reads the page
  (`lookupVendorComponent`) and fills the new component and its vendor listing.
  This needs only `LABKIT_GEMINI_API_KEY` and a new deployment, and the model must
  support Google Search grounding (`gemini-2.5-flash` or newer). Prices are read
  from web pages by an AI, so they are saved as unverified until an officer
  confirms them, and every plan that uses one says so. Some vendor sites block
  automated readers; then the officer can paste the listing text
  (`parseNewComponentText`), or type the fields by hand. Search grounding may be
  billed or limited separately from plain Gemini calls, so check Google's current
  pricing page. The Mouser, DigiKey and Newark credentials above are used only by
  "Refresh supplier quotes".
- **Estimates stay labeled.** Existing design estimates remain useful before
  credentials are configured, but a verified acceptable API quote takes
  priority in cheapest-price calculations.
- **Other stores are explicit manual checks.** Amazon and AliExpress require
  marketplace/affiliate approval for useful product APIs, LCSC restricts its
  official API to approved partners, and no public Jameco pricing API is relied
  on here. LabKit opens searches for Amazon, Jameco, LCSC, AliExpress, and
  Alibaba, but never scrapes or relabels those results as verified prices.

## Access model

- Firebase handles the dedicated account's password, verification email,
  password reset, and identity.
- Every backend request sends the current Firebase ID token.
- Apps Script verifies that token directly with Firebase and requires the exact
  configured HKN Lab Supplies email. It records the verified Firebase UID in
  `Users` for auditing; additional accounts cannot be granted access.
- Writes use a script lock, optimistic version checking, request IDs, and an
  append-only audit entry so accidental double submissions do not create two
  saves.
- The first signed-in browser receives a 90-second renewable editor lease.
  Other signed-in browsers are view-only, poll for live updates, and take over
  automatically after the editor signs out or stops renewing the lease.
- The web app debounces shared saves and excludes navigation/dialog state. The
  backend rejects every write whose session does not own the editor lease, and
  version checks still prevent stale writes.

The Firebase web API key is a public project identifier, not an administrator
secret. Sheet access is protected by the verified dedicated Firebase account.
Never add a Firebase service-account private key to this project or the browser
app.
